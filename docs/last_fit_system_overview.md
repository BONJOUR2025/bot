# Подбор колодки по 3D-скану — обзор текущей системы

Снимок состояния на сегодня: что реализовано, какими средствами, и на каком
этапе зрелости находится система. Написан как справочная точка входа —
детали порогов и вердиктов см. в [`last_fit_verdicts.md`](last_fit_verdicts.md),
детали известных архитектурных недочётов — во внешнем аудите
`audit_nedochety_tekushchey_sistemy_podbora_kolodki.md`.

## 1. Что система делает сейчас

Пользователь (админ-панель, `Scanner3D.jsx` → вкладка «Библиотека колодок»,
`LastLibrary.jsx`) может:

1. Загрузить скан колодки (`.scm` или `.stl`) в библиотеку с метаданными
   (артикул, размер, модель, материал, сторона).
2. Загрузить скан стопы клиента (один `.scm` с обеими стопами, либо два
   отдельных `.stl` — левая/правая) и получить:
   - геометрические измерения каждой стопы (длина/ширина/высота/обхваты);
   - ранжированный список колодок из библиотеки от «лучше всего подходит»
     до «не подходит»;
   - для каждой пары стопа/колодка — вердикт по 5 зонам (пятка, свод,
     подъём, пучки, носок), картинки-наложения (вид сверху и сбоку,
     колодка серым, стопа синим, конфликтные точки красным), жёсткие
     причины отказа, если есть.

Это инструмент подбора «какая из уже имеющихся колодок подойдёт» и
диагностики «где именно и почему жмёт/свободно» — не CAD-система
проектирования новой колодки.

## 2. Конвейер данных

```
Загрузка файла (.scm / .stl)
        │
        ▼
Парсер формата → облако точек (x, y, z) в мм,
                  система координат: Y = длина от пятки (пятка = 0),
                  Z = высота от подошвы (0 = пол), X = медиально-латерально
        │
        ▼
Фильтр выбросов (перцентильный, + обрезка изолированных краевых точек)
        │
        ▼
Профиль сечений: 70 срезов вдоль длины, в каждом —
   medial (край), lateral (край), top (высота), girth (периметр среза)
        │
        ├─→ Обхват пучков (наклонный срез по MTH1/MTH5-ориентирам)
        ├─→ Обхват подъёма (перпендикулярный срез на ~50% длины)
        └─→ Линия сгиба пучков (положение MTH1/MTH5 вдоль длины)
        │
        ▼
Для колодки: профиль + обхваты сохраняются в lasts.json (парсится один раз
              при загрузке, дальше переиспользуется)
Для стопы:   профиль + обхваты считаются на лету при каждом запросе /match
        │
        ▼
Сравнение профилей (last_fit_service.compare_profiles):
   ресемплинг обоих профилей на общую сетку длины,
   расчёт ease (запас) по обхвату/ширине/высоте на срез,
   агрегация в 5 именованных зон, вердикт на зону, общий вердикт
        │
        ▼
Рендер наложений (matplotlib, Agg-backend) → PNG → base64 → JSON-ответ
```

## 3. Технические подходы по стадиям конвейера

### 3.1. Извлечение геометрии из файла

Два формата, два парсера, единый результат (облако точек + измерения):

- **`.scm`** (`app/services/scm_parser_service.py`) — проприетарный,
  недокументированный формат сканера. Это ZIP-контейнер с одним файлом
  внутри: текстовый заголовок (UTF-16LE) с именем/телефоном/датой скана,
  за которым идут мегабайты бинарных данных без документированной
  раскладки. Подход: **эвристический скан байтов** — файл читается как
  float32-массив на всех 4 возможных выравниваниях, ищутся длинные
  участки, где каждое значение — конечное число небольшой величины
  (миллиметровый масштаб). Такие участки почти наверняка — облако точек
  XYZ; подтверждено вручную (восстановленные точки складываются в
  анатомически верную стопу — пальцы, свод, пятка). Это официально
  задокументировано в коде как «best effort», не сертифицированный метод.
- **`.stl`** (`app/services/stl_parser_service.py`, добавлено в этой сессии)
  — стандартный формат, бинарный (header 80 байт + uint32 количество
  треугольников + 50 байт/треугольник) с ASCII-фолбэком. У сканера — один
  файл = одна сторона (левая/правая отдельными файлами), в отличие от
  `.scm`, где один файл = обе стопы (или одна колодка). Координатная
  система идентична `.scm` (проверено на реальном образце) — поэтому вся
  геометрия сравнения переиспользуется без изменений.

**Важное ограничение обоих парсеров:** несмотря на то, что `.stl` по
формату — полноценная триангулированная сетка (грани, нормали), парсер
**выбрасывает топологию** и оставляет только координаты вершин
(`np.unique` по вершинам треугольников). Итог: и `.scm`, и `.stl`
после парсинга — это **голое облако точек**, не сетка. Индексы
треугольников, нормали, связность поверхности нигде дальше не
используются.

### 3.2. Гигиена данных

- `_strip_outlier_points` — перцентильная (0.1–99.9%) отбраковка по каждой
  оси + обрезка изолированных краевых точек (одиночные точки, оторванные
  от основного кластера зазором > 3 мм) — защита от шума сканера и
  артефактов опорной платформы.
- Анатомическая валидация bounding box (длина 100–400 мм, ширина 30–200 мм,
  высота 15–300 мм, длина > ширины) — отбраковка нефутовой геометрии на
  входе.

### 3.3. Измерения

- **Профиль сечений** (`extract_profile`) — облако точек режется на 70
  срезов вдоль оси длины (Y), в каждом срезе на площадку следа (высота
  ≤ 30 мм) берутся перцентили 98/2 по X как medial/lateral край, перцентиль
  99 по Z как высота, периметр выпуклой оболочки (X, Z) как обхват среза.
  Это **плоскостной**, а не объёмный анализ — каждое сечение сводится к
  4 скалярам.
- **Обхват пучков** — не простой перпендикулярный срез (даёт ошибку
  3–9 мм против эталона), а срез, наклонённый по линии между медиальным и
  латеральным «бугром» (ориентиры MTH1/MTH5), найденными в зоне 50–80%
  длины. Откалибровано по 3 эталонным сканам до 1.6–3.6 мм.
- **Обхват подъёма** — перпендикулярный срез на ~50% длины (плюс отчёт по
  5 соседним сечениям 40/45/50/55/60%, так как в отрасли нет единого
  определения, где именно «подъём»).
- **Выпуклая оболочка** — собственная реализация monotone chain (без
  scipy), периметр как обхват среза.

### 3.4. Сравнение стопа/колодка

`app/services/last_fit_service.py`, функция `compare_profiles`:

- Оба профиля ресемплируются (`np.interp`) на общую сетку длины стопы.
- Для каждого среза считается ease (запас = колодка − стопа) отдельно по
  обхвату, медиальному/латеральному краю, высоте.
- Пересечение (protrusion) и избыток (excess) вычисляются геометрически —
  прямое наложение контуров, не через обхват.
- 5 именованных зон (пятка/свод/подъём/пучки/носок, доли длины стопы) —
  для каждой берётся устойчивый перцентиль (P10/P90) ease внутри зоны, а
  не сырой min/max, чтобы одна шумная точка не решала вердикт зоны.
- Порог неопределённости (`GIRTH_UNCERTAINTY_MM = 4 мм`, единый на все
  зоны и метрики обхвата) — разница внутри этого порога даёт вердикт
  `uncertain` вместо уверенного tight/loose.
- Отдельный слой «жёстких причин отказа» (`hard_fail_reasons`) — протрузия
  > 6 мм, отрицательный запас по длине, смещение линии сгиба > 10 мм —
  не усредняется с остальными зонами, форсирует `not_fit`.
- Разбор по источнику: асимметричный избыток ширины требует запаса **с
  обеих сторон одновременно** — односторонний зазор трактуется как
  смещение сканов, а не реальная свобода.
- Пороги (5–10 мм пучки, 5–11 мм подъём, 8–15 мм длина и т.д.) — не
  универсальный стандарт, а инженерные стартовые значения из ГОСТ
  3927-88, bespoke-источников и нескольких научных работ (см. цитаты в
  самом файле и в `3d_scan_last_selection_technical.md`), пока не
  откалиброванные на реальных примерках BONJOUR.

### 3.5. Визуализация

`matplotlib` (`Figure` + `FigureCanvasAgg` напрямую, не `pyplot` — чтобы
не ловить гонки между потоками при параллельных запросах через
`asyncio.to_thread`): вид сверху (footprint) и сбоку, колодка залита
серым, контур стопы синим, точки конфликта — красным.

## 4. Хранение данных

- **Библиотека колодок** — плоский JSON-файл `lasts.json`
  (`app/data/last_repository.py`), без БД: список записей с метаданными +
  посчитанный профиль (пересчитывается один раз при загрузке).
- **Сырые файлы сканов** — `static/uploads/lasts/{id}.scm` или
  `{id}.stl`, отдаются как статика.
- **Скан стопы для сравнения** — не сохраняется вовсе, парсится и
  сравнивается на лету при каждом запросе `/lasts/match`.

## 5. API и фронтенд

- `app/api/lasts.py` — `GET/POST/DELETE /lasts` (библиотека), `POST
  /lasts/match` (сравнение). CPU-тяжёлые операции (парсинг, ресемплинг,
  рендер) вынесены через `asyncio.to_thread`, чтобы не блокировать event
  loop.
- `admin_frontend/src/pages/LastLibrary.jsx` (+ `FootScanCard.jsx`,
  переиспользуется со `Scanner3D.jsx`) — загрузка, список библиотеки,
  загрузка скана стопы (одним `.scm` или парой `.stl`), карточки
  результата с бейджами вердиктов, картинками-наложениями и
  разворачиваемыми пояснениями по зонам.

## 6. Инструменты и зависимости

- `numpy` — вся числовая обработка (парсинг, фильтрация, профиль).
- `matplotlib` — рендер наложений в PNG.
- Собственная реализация выпуклой оболочки (monotone chain) — **scipy не
  используется и не установлен**.
- **`trimesh`/`numpy-stl` не установлены** — поэтому `.stl` парсится
  вручную через `struct`, без библиотеки для работы с сетками.
- FastAPI (API), React 19 + Vite + Tailwind (админка).
- Нет внешних геометрических/CAD-библиотек, нет GPU, нет ML-компонента —
  вся логика деterministic и объяснимая (правила + пороги), что и
  позволяет писать человеко-читаемые тексты вердиктов.

## 7. На каком этапе зрелости это находится

Честная оценка, подтверждённая построчной сверкой с внешним аудитом
(`audit_nedochety_tekushchey_sistemy_podbora_kolodki.md`):

- Это **работающий, объяснимый геометрический фильтр** первого уровня:
  сравнение по срезам с понятными людям порогами и текстами — полезно
  как первичный отсев и справочник по отдельным параметрам.
- Это **ещё не полноценная система прогноза комфорта**. Ключевые
  архитектурные пробелы (детали — во внешнем аудите, статус сверен в этой
  сессии — из 20 пунктов ни один не закрыт полностью, 3 закрыты частично):
  - геометрия — облако точек, не сетка (топология выбрасывается даже у
    `.stl`);
  - сравнение — стек 2D-срезов, не знаковая 3D-карта расстояний
    поверхность↔поверхность;
  - нет позы (высота каблука, носочный подъём) — стопа и колодка
    сравниваются «плоско», хотя колодка объёмная и с посадкой на каблук;
  - нет доверительных оценок совмещения/скана (geometric confidence);
  - нет модели удержания пятки, резерва шнуровки, динамики стопы при
    ходьбе;
  - нет калибровки порогов на реальных примерках — все числа инженерные,
    не подтверждённые;
  - вердикты внутри зоны — «победитель забирает всё» (if/elif), а не
    комбинация одновременных сигналов.
- Следующий содержательный шаг для перехода на «настоящую 3D-модель» —
  сохранять треугольники при парсинге `.stl` и считать знаковое
  расстояние точка↔поверхность (mesh distance) вместо срезовых скаляров;
  это потребует библиотеки работы с сетками (например `trimesh`),
  которой сейчас в окружении нет.
